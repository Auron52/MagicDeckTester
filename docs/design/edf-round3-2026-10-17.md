## 1. Determinism: the rollout oracle never cleared the per-game caches

`TurnSolver::ClearPerGameCaches` ran only from `AIEngine::HandleMulligan`, i.e. only for games entered through
`GameEngine::RunGame` (the batch runner, GoldFishRunner, AnalyzerEngine, the keep generator's play-digest games,
single `mtg` games). Every generator that scores rollouts through `AIEngine::RolloutKeepWinTurn` skipped it:

* the exhaustive keep generator itself (`--gen-mulligan`, i.e. `scripts/mullgen.sh`: `run_batch`, `run_one`,
  plus `MTG_KEEP_BENCH` / `MTG_KEEP_REPLAY`),
* equivalence discovery (`EquivalenceDiscovery.cpp`),
* the keep-model trainer (`KeepModelTrainer.cpp`),
* the comp scorer (`MTG_SCORE_*`) and the MULL-EV probe (analyzer `main.cpp`).

So the plan memos, the bp-enum cache, the combo-route memo, the payable-mana cache and the hybrid's learned R/G
carried from one rollout into the next on a reused worker, and the work-stealing order decided which rollouts shared
one. Fix: `RolloutKeepWinTurn` clears at entry (before `BottomCards`); every caller is a generator and none calls it
from inside a game. `MTG_LEGACY_ROLLOUT_KEEP_CACHE_CARRY=1` restores the carry.

**Measured** (the real generator path, `MTG_KEEP_BENCH` per-rollout dumps; `logs/edf_r3/keepbenchg.sh`,
`cmpdump.py`):

| run | per-rollout win turn | per-rollout units |
|---|---|---|
| EDF d1 b1, 160 rollouts: base 1 thr vs 16 thr | identical | identical |
| EDF d1 b1: fixed vs base | identical | identical |
| Kitty d5 b20, 240 rollouts, TT cap pinned: **base** 1 thr vs 16 thr | identical | **7 differ** (net -15,423 of 5.06M) |
| Kitty d5 b20, TT cap pinned: **fixed** 1 thr vs 16 thr | identical | **identical** |
| Kitty comp scorer d5 b20 (128 rollouts): base 1 thr / 16 thr | labels identical | 1,843,793 / 1,844,833 units |
| same, fixed 1 thr / 16 thr | labels identical | 1,843,137 / 1,843,137 |

So on EDF at the generation shape the outputs did not change (no cache key repeats across rollouts there, as the
previous round found), and on a deck where they do repeat (Kitty d5) the carry moved work units in ~3% of rollouts
and the fix makes every rollout a function of itself (Kitty bench rollout 93 re-run ALONE via `MTG_KEEP_REPLAY`:
116,889 units, the fixed 1- and 16-thread value). No win turn moved in any sample. Cost: +0.09% instructions on the
EDF probe.

**Residual, not fixed (pre-existing, thread-COUNT not interleaving):** `MemBudget` sizes the transposition table per
worker (`cache_mb / workers`), so a run at 16 threads has a smaller TT than at 1 and units can differ by thread
count. With `MTG_TT_CAP` pinned the fixed generator is byte-identical across thread counts. The shared plan-cache /
FSL pools are the other cross-thread channel; they print the `[determinism] WARNING` when they bind. A generation is
reproducible at a FIXED thread count and memory budget; across thread counts only with `MTG_TT_CAP` pinned.

## 2. `MTG_PLAN_SIG_FAST` (default ON): the plan signature in one arena

`EnumeratePlans`' dedup key built each per-action token as its own `std::string` into seven `vector<string>`s.
`PlanSignatureFast` writes all tokens into one reused `thread_local` arena, sorts (bucket, span) pairs in
`std::string` order and concatenates with the same letters: the IDENTICAL string (the old concatenation is not
injective, so an "equivalent" key could change dedup decisions -- the exact string is the only safe target). Human
play keeps the legacy builder. Every token mirrors the legacy lambda field for field; both carry a LOCKSTEP comment,
and `MTG_PLAN_SIG_FAST_VERIFY=1` builds both, returns the legacy string and counts differences.

* Probe: **-6.7% instructions** (611.33e9 -> 570.17e9, 2+2 alternating runs, labels identical).
* Identity batch: -6.1% instructions; on / off / verify identical; verify **27,753,607 signatures, MISMATCH=0**.
* Follow-up: the span's bucket field widened to 32 bits (a byte store then a dword load of the same Span was a
  store-forwarding stall on the builder's hottest line).

| change | result | kept? |
|---|---|---|

Note for the next round: `instructions:u` undercounts `rep movsb` copies (one instruction moves kilobytes), so a
change that trades a memmove for anything else must be judged on `cycles:u` as well (`logs/edf_r3/ab.sh` records
both).

Open per-node items (none byte-identical-trivial): the payability probes' full GameState copy into the warm board
(the payer READS the library for the reveal/refloat demand, so the library cannot simply be skipped -- it would need
a probe-local view); `ManaCacheKey`'s full battlefield walk on every backtracker entry (3.5% inclusive); the GameState
copies in the combo route.
