# Byte-identical engine speed pass, 2026-09-11

A pure-performance pass: every change here leaves the engine's decisions bit-for-bit unchanged
(verified by the full gate suite — see **Verification** at the bottom). No heuristic, ordering,
tie-break or floating-point path was touched.

## Method

The box was shared with other agents throughout, so **wall clock was not the primary instrument**.
Everything was measured with `valgrind --tool=callgrind --cache-sim=no --branch-sim=no` on
`build/Profile/mtg` (`./build.sh profile` — Release codegen plus symbols), single-threaded, on a
fixed seed. Instruction counts are deterministic and load-independent, so an A/B is exact.

Two collection modes, because they answer different questions:

| mode | invocation | what it counts |
|---|---|---|
| whole-process | `valgrind --tool=callgrind … mtg --batch <m> --threads 1` | startup + play + teardown |
| in-game only | `… --toggle-collect='GameEngine::RunGame*' …` | only what runs inside a game |

The split is not cosmetic. A short run's whole-process profile is **dominated by startup**: the
exhaustive keep sidecar deserialize was 85% of a 6-game goblins run. `docs/design/engine-cost-profile-2026-08-16.md`
warned about exactly this ("startup swamps a short run"); the toggle is how this pass avoided it.

Four configs, taken from `test/regression_cases.sh` so they are configurations the suite really runs:

| tag | case | why |
|---|---|---|
| `goblins` | `goblins 3 1001 … 10` (`depth` pinned, `ignore_play_profile`) | searched-depth aggro |
| `dragonstorm` | `dragonstorm 5 1001 … 20` (depth key dropped → `value_play` owns it) | combo deck, heavy enumeration |
| `kitty` | `kitty 5 1001 … 20` (same) | ships an adopted keep model **and** a value leaf |
| `fluctuator` | `fluctuator 3 1001 … 10` | combo/cycling, and the one config with **no keep sidecar** — the control for every startup change |

Manifests are in `logs/perf/cg_*.json` (whole-process) and `logs/perf/cgg_*.json` (in-game), runners
in `logs/perf/cg_run.sh` / `logs/perf/cgg_run.sh`, and the two analysis helpers used below are
`logs/perf/cgline.py` (per-source-line self cost for one function) and `logs/perf/cmp.py` (Ir diff
between two run directories).

### One measurement caveat worth recording

Callgrind counts each iteration of a `rep movsb`/`rep stosb` string operation as an executed
instruction. Large ERMS `memset`/`memcpy` therefore show up at **~1 Ir per byte** while running at
tens of GB/s in reality. The 596 MB `blob.resize()` in `CachedExhaustiveKeep` is exactly this shape
(596,097,503 Ir ≈ the file's byte count), so it looks like a giant cost and is worth only tens of
milliseconds. Do not chase it, and do not read bulk-copy Ir as if it were ordinary code.

## What changed

### 1. `perf(bincache)` — sorted-hint map append + bulk int-vector decode

`src/ai/MulliganProfileIO.h`. Two defects in `DeserializeExhaustiveKeep`:

* `ek.keep` / `ek.bottom_keep` are `std::map<std::vector<int>, …>`, and `SerializeExhaustiveKeep`
  writes them by walking the map — so the blob's composition keys are strictly **ascending**. Every
  insert nonetheless used plain `emplace`, which re-walks the red-black tree from the root doing
  lexicographic `vector<int>` comparisons at each level. `emplace_hint(m.end(), …)` takes libstdc++'s
  O(1) rightmost-append path. Result-identical, and *not* dependent on the blob being sorted: a bad
  hint only costs the ordinary search, and `_unique` still rejects duplicates.
* `GetIVec` did one `end - p` bounds test and one 4-byte `memcpy` **per element**. Now: one length
  check for the whole array, then a single `memcpy`. Checking the byte budget *before* `resize(n)`
  is also strictly safer — the old order could try to allocate 16 GB off a corrupt count.

| config | before | after | delta |
|---|---|---|---|
| goblins (whole-process) | 7,765,581,577 | 3,990,323,892 | **−48.62%** |
| dragonstorm | 2,302,545,051 | 1,209,143,076 | **−47.49%** |
| kitty | 5,254,591,121 | 4,050,889,151 | **−22.91%** |
| fluctuator (no sidecar — control) | 41,182,370,135 | 41,182,095,252 | −0.00% |
| `CachedExhaustiveKeep` alone (goblins, inclusive) | 6,629,636,725 | 2,854,346,728 | **−56.9%** |

### 2. `perf(flags)` — four hot `EnvOn` reads were not `static`

`src/ai/ManaPayment.cpp` (`BuildColorFeasibility`: `MTG_DOMAIN_WIDEN`) and `src/ai/TurnSolver.cpp`
(`SubsetPayableSequential` + `exec_feas_rescues` ×2: `MTG_DBG_SEQ`). All four sit on per-candidate-subset
paths and re-walked `environ` on every call. The two `MTG_DBG_SEQ` sites cost that while printing
nothing — the branch has to evaluate the flag to decide not to print.

Fixed with **function-local** statics (not file-scope), so the read still happens on first use, after
`main()`'s `ApplyHeuristicDefaults` — which is what the ~40 other flag reads in these files already do.

| config (in-game Ir) | before | after | delta |
|---|---|---|---|
| goblins | 4,309,129,068 | 4,247,597,885 | **−1.43%** |
| dragonstorm | 2,764,115,304 | 2,729,802,146 | **−1.24%** |
| kitty | 24,874,014,203 | 24,311,454,829 | **−2.26%** |
| fluctuator (whole-process) | 41,182,095,252 | 40,859,592,788 | **−0.78%** |

### 3. `perf(strings)` — `std::string == "literal"` in two hot helpers

`src/core/SpellEffects.h`. `operator==(const std::string&, const char*)` did not inline in this
build, so each comparison was an out-of-line call that `strlen`s the literal and then compares.

* `CardMatchesTypeName` ran **six** of them before falling through to the subtype scan — and a
  subtype tutor ("Dragon", "Sliver", "Goblin") misses all six. Now `std::string_view` compares,
  whose literal length is a compile-time constant, so each test is usually one size compare.
* `AddColorToPool` compared a one-character colour string against six one-character literals. Now a
  `switch` on `col[0]` guarded by `col.size() == 1`; empty and unknown still land on wild, exactly
  as the old chain did.

### 4. `perf(lords)` — skip the conditional-anthem battlefield walk when no card can match

`src/core/SpellEffects.h` + `src/cards/CardDatabase.{h,cpp}`. `ComputeLordBonus` ended with an
**unconditional** full-battlefield walk (a `LookupCached` per controller-owned permanent) looking for
`CardParams::hand_size_anthem_max` — a clause exactly ONE card in `cards.json` carries (Neheb, the
Worthy, threshold 1). Its own comment claimed the scan was "skipped entirely unless the state
actually holds such a permanent"; no such guard existed.

Every iteration ends in `if (hand_size > sd->params.hand_size_anthem_max) continue;`, so when the
controller's hand is bigger than the **largest such threshold in the loaded card data**, no permanent
can pass and the walk is provably a no-op. `CardDatabase::MaxHandSizeAnthemMax()` is that bound: a
derived constant of `cards.json`, refreshed by `RebuildInternedIndex` and immutable during play.
Nothing about a deck or a game state is assumed — it is a property of the data the process loaded.

### 5. `perf(sidecar)` — do not free the process-lifetime keep-policy cache at exit

`src/ai/MulliganProfileIO.h`. `CachedExhaustiveKeep`'s process-global map is destroyed during static
teardown, and `~ExhaustiveKeepPolicy` walks two red-black trees node by node to free them:
15.0% (goblins) / 13.4% (dragonstorm) of a short run's instructions, spent after the process has
produced all of its output. The cache is now heap-allocated and never deleted, so the OS reclaims the
pages instead. Nothing observable changes; it also removes a static-destruction-order hazard. (No CI
job runs a leak checker — checked `.github/workflows/`.)

## Measured and rejected

| candidate | measurement | verdict |
|---|---|---|
| `thread_local` scratch for `BuildSimKey`'s `canon_items` vector (removes one `new`/`delete` pair per call) | `operator new` 26.2M + `operator delete` 13.7M = 0.16% of kitty in-game; 0.26% on fluctuator | **rejected** — under the 0.5% bar on every config, and it makes a re-entrancy hazard out of a function that currently has none |
| Cheapen `Fold()` (the 128-bit key mixer) | 61% of `BuildSimKey`'s self cost, i.e. 4.55% of kitty in-game — but it is already ~12 instructions and the chain is serially dependent | **rejected** — cannot be made cheaper without changing the hash, which changes memo collisions and is therefore not byte-identical |
| `MidGameEvaluator::Score` (value leaf), 4.94% kitty / 2.53% dragonstorm | — | **not attempted** — it is a float dot product; any reassociation changes results. Explicitly out of scope |
| `CardDatabase::Lookup(const std::string&)` in `ApplyPlanDirect`'s dig loop, 0.95% of fluctuator | the name comes from `DecisionProvider::SelectDigSource`, which returns `std::string` by value | **deferred** — the fix is to make the provider hook return an `InternedName` so the call can use `LookupInterned`; that is a virtual-interface change across every provider, too wide for a byte-identical pass |
| `GenericProvider::TutorCandidates` string compares (0.26% kitty, 0.75% goblins) | per-candidate `std::string` name equality | **deferred** — same interned-name fix, same reason |
| The 596 MB `blob.resize()` zero-fill in `CachedExhaustiveKeep` (596M Ir) | ERMS `memset`; ~1 Ir/byte in callgrind, ~20–60 ms in reality | **rejected** — the Ir number is an artifact of how valgrind counts `rep stosb`; avoiding it needs C++23 `resize_and_overwrite` or an API change, for a real saving in the tens of milliseconds |

## Verification

Every commit was gated individually with `bash test/regression.sh --smoke`, which must print
`configs changed: 0` and `play-changed=0`. The final tree additionally passed the full
`bash test/regression.sh` (99 configs), `bash test/scenarios.sh`, `bash test/combo_off_check.sh`,
`bash test/viewer_checks.sh` and `build/Release/mtg-test`. The exact gate lines are in the session
report accompanying these commits.

## If you pick this up next

The two biggest remaining in-game items are `BuildSimKey` (4–9%) and `CardDatabase::LookupCached`
(2.9–7.2%), and neither is reducible by making the function faster — both are dominated by **call
count**. `LookupCached`'s largest single caller is `ComputeLordBonus` on every deck measured, which
change 4 above only partly addresses. The next honest step is to cut calls, not cycles: a
`Permanent`-side cache of the handful of `CardParams` booleans the hot scans read would remove most
of them, but it is a data-model change and needs its own byte-identity argument.
