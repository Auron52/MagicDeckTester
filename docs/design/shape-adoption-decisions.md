# Per-deck search-shape adoption: the decision sheet

**Status (2026-09-11):** every mode cell is measured. Nothing here is adopted. This document exists
so the remaining work is *rulings*, not measurement.

Reading the tables: **Δ < 0 means fewer turns to win = BETTER.** `±se` is the standard error over 16
blocks of 250 games (4,000 games/cell). `bett/wors` counts individual games whose win turn moved.

**Cost is judged on UNITS, never wall.** Every screen here shared a box, and the plan-cache pool is
now global, so one arm's monster enumeration can draw pool another arm wanted. Units are the work
actually done. The clearest proof that wall lies: breaching `cap` and `capctl` are both
**byte-identical play at units 1.000x**, yet report 0.859x and 0.822x wall. Neither is a speedup.

A **CLEAN WIN** must not regress on *any* axis versus the shipped baseline. A cell where some games
got worse is not a clean win however cheap it is, even if the mean is inside the noise band.

## 1. The single most important fact: `escalation_cap` IS the one-depth switch

`TurnSolver.cpp:36126`:

```cpp
const bool eff_single_deck = !s_esc_single_env && escalation_cap > 0;
```

The single-depth predicted-affordable escalation is driven by **`escalation_cap > 0`**, not by
`value_play.ladder`. `ladder: "single"` is a *different* mechanism (ValueArm's "FIT single pass",
`t_deck_single = 2`). So:

* the **12 decks that ship `escalation_cap`** already run one depth on-policy;
* the **8 decks that do not** run the full escalation ladder.

`escalation_cap` is also gated on `vp_here` (`drives() && lookahead_depth == target_depth`), so even
a capped deck reverts to the full ladder off-policy.

**Therefore "I don't want full ladder anywhere" = give the remaining 8 decks a cap.** That is exactly
what the `cap` arm measured, and the answer is mostly yes — with one real obstruction (§4).

## 4. Why the ladder sometimes beats one depth — and why that is a defect, not a mode

Two decks lose real quality when forced to one depth: **Melira** (`cap` = **+0.0208 ± 0.0027**,
8 better / 77 worse) and **Creature Giving** (`nocap` gains −0.0045, i.e. the ladder is better).

Diagnosed mechanism, and the two decks fail for **opposite** reasons — which is why no single
constant fixes it:

* **Melira — the crossover is being defeated.** Melira's `value_fallback_crossover` is
  `take_heuristic_at_hdepth = [1, 2, 3, 4, 5, 5, 6, 6]`, the identity for c ≤ 5. Every other deck
  in the repo starts `[1, 1, 1, 2, …]`. So Melira prefers its **value** line far more strongly than
  any other deck. Measured commit depths: the ladder commits mean **1.39** (h1:24, h2:5, h3:4), the
  single pass **2.30** (h1:7, h2:13, h3:9, h4:4), with `abort_first=0 fellback=0 wasted_units=0`.
  The ladder therefore wins **by committing too shallow to pass `take_at`**, which preserves the
  value line. It is not doing useful extra work; it is accidentally protecting a line the crossover
  would otherwise discard.
* **Creature Giving — the affordability predictor is too pessimistic.** Here the ladder commits
  *deeper* (2.98 vs 2.30): its shallow passes **prime the memo**, so the d3 pass completes where the
  cold-cost predictor refuses to start it.

So the predictor mispredicts in **both directions**, and on Melira the crossover table it feeds is
**self-declared stale** — the provenance reads *"value_leaf_table/crossover here are the OLD ones
until the regenerated matrix lands."* 14 of 20 decks carry that same note.

**This is the ONE DEPTH blocker, and it is two fixes, not one:**
1. regenerate Melira's crossover on the current commit (a full value-leaf run, hours); and
2. make the single pass anytime-climbing so it keeps the memo-priming benefit the ladder gets for
   free (a code change — *awaiting your call*).

Until then, one depth is adoptable on the other 18 decks and **must not** be forced on Melira or
Creature Giving.

## 6. The three activation regimes — the real footgun

A key's presence in a sidecar does **not** mean it is live. There are three tiers, invisible in the
JSON:

| tier | gate | keys |
|---|---|---|
| always, at load | sidecar exists | `leaf`, `alpha`, `ladder`, `commit`, `exhaust_mult` |
| `drives()` | `target_depth > 0 && enabled` | `beam_width`, `beam_leafdepth` |
| `vp_here` | `drives() && lookahead_depth == target_depth` | `escalation_cap`, `escalation_r`, `escalation_fresh_frac` |

Consequences that already bit us:

* **KittyEquipment ships `target_depth: 5, budget_ms: 20, enabled: false`.** It looks configured and
  is entirely inert.
* **The earlier `escalation_fresh_frac` screen was meaningless.** It ran on decks that *lack* the
  key, where `drives()` is false and frac cannot do anything — hence a wall of `IDENTICAL` read as
  "frac does nothing". The re-run added an `en` control (drives() on, nothing else), which is
  byte-identical 16/16, so `enfrac`'s movement is attributable to frac alone.
* **OFF for frac is `-1`, not `0`.** `-1` = legacy shared remaining budget; `0.0` = a fresh budget of
  `max(1, round(0 × budget_ms))` = **1 ms**, a pathological sliver (`MulliganProfile.h:72`,
  `TurnSolver.cpp:36556`).

The no-leaf family answers the "no leaf early, leaf at the final depth" question for Melira: **no.**
It ties on quality and pays ~70% more wall. The fresh-budget dial (0.5 → 0.25 → 0.125) moved quality
by 0.0005, well inside ±0.0061, so the expense is the leafless search itself, not the fresh budget.

**Ordering requirement.** `mull_gen_depth`/`mull_gen_budget_ms` come from `value_play`, and the
mulligan generator fits whatever play is shipped. So:

* Melira already has its gen settings (`d3` / `b3`, 23 buckets) — **the gen is not blocked.**
* If `enfrac` is adopted for Melira, it **must land and freeze before** the gen starts, or the
  profile fits play we will not ship.
* If Melira's stale crossover is ever regenerated, **that invalidates the mulligan profile** and it
  must be rebuilt. Regenerating first costs hours; shipping as-is costs nothing and is the
  best-measured configuration. Recommendation: **ship as-is, generate, revisit the crossover with
  the one-depth project.**
